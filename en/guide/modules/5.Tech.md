<a id="module-folder-structure"></a>
### Module Folder Structure

The following files can be present in the module root directory:

- `module.json` - the main file with module information (required)
- `scripts/main.lua` - code executed on the client side (required)
- `scripts/server.lua` - code executed on the server side
- `config.json` - module user settings
- [`inputs.json`](#module-inputs-json) - custom module key bindings
- `localization.csv` - a table with translations for different languages

The directory can also contain optional resource folders:

- `sounds/` - folder for sound files, supported format: `wav`
- `images/` - folder for image files, supported format: `png`
- `scripts/` - folder for script files, supported format: `lua`
- `ui/` - folder for UI files, supported formats: `uxml`, `uss`

<a id="module-tags"></a>
### Module Tags

In `module.json`, the module has a `Tags` field. This is an array of tags used to group modules by purpose and to show warnings when features overlap.

Example:

```json
{
  "Tags": ["Crosshair", "Notifications"]
}
```

A module can:

- have no tags
- have one tag
- have multiple tags

If there are no tags, the module simply falls into the untagged group. If there are multiple tags, the game treats the module as belonging to several categories at once.

Available tags:

- `Minimap` - minimap modules
- `PingMarks` - marker and ping modules
- `OverheadLabels` - labels and elements above objects
- `Crosshair` - crosshairs and related HUD elements
- `Health` - health display
- `Notifications` - on-screen notifications
- `MatchStatus` - match, round, and phase status
- `CombatReport` - combat report
- `Scoreboard` - scoreboard
- `Loadout` - loadout and equipment information
- `BuyMenu` - buy menu
- `GrenadePreview` - grenade previews and trajectories
- `Chat` - chat
- `ThreatIndicator` - grenade and danger direction indicators
- `KillFeed` - kill feed
- `Spectator` - spectator interface
- `DebugInfo` - debug information

### Tag Conflicts

If two or more active modules share the same tag, the game marks them as conflicting. This is not a hard block: such modules can still run at the same time.

The important thing to understand is that a tag conflict means overlapping functionality. For example, two modules with the `Crosshair` tag may both draw their own crosshair at the same time, and two modules with the `Notifications` tag may both display similar notifications.

In other words, tag conflicts primarily affect the interface and the behavior of modules: they warn you that several modules are trying to solve the same task. Regular tags do not automatically prevent a module from running.

<a id="reflex-flag"></a>
### Reflex Flag

`Reflex` is a separate `IsReflex` flag in `module.json`.

Example:

```json
{
  "IsReflex": true,
  "Tags": []
}
```

A module with this flag differs from a regular one because it has a server-side part in the `scripts/server.lua` file. When a player joins a server, the game takes the code from this file on the client and sends it to the server for execution.

Reflex modules have a separate limitation: only one such module can be running at the same time. This behavior is unrelated to tags and works separately from the tag conflict system.

### Execution Time Limits

During the initial initialization of `main.lua`, a module gets 5 seconds. If this limit is exceeded, the module will be disabled until the next restart.

There are also execution time limits for a single client frame and a single server tick. Client modules are limited to `200 ms` per frame. This is a very generous limit intended only to prevent the game from freezing completely: hitting it would leave the game running at 5 frames per second. Server modules have a stricter limit of `1 ms` per server tick.

When a module reaches the limit, its execution is suspended and resumes from the same point on the next frame or tick.

<a id="module-inputs-json"></a>
### inputs.json File

`inputs.json` is placed in the module root and describes custom input actions that the module adds to the game's control system.

Minimal example:

```json
{
  "Actions": [
    {
      "Name": "ToggleSniperMode",
      "Type": "Button",
      "Binding": {
        "Path": "<Keyboard>/v"
      }
    }
  ]
}
```

The file consists of an `Actions` array. Each element describes one action.

- `Name` - the action name. The module later looks it up through [`InputActions:FindAction`](../../api/InputAction.md#findaction).
- `Type` - the action type. Supported values are `Button`, `Value`, and `PassThrough`. If the field is omitted, the game uses `Button`.
- `Binding` - the description of the default key or other control binding.

Inside `Binding`, you can set:

- `Path` - the control path in Unity Input System format. This is the main required field, for example `<Keyboard>/v`, `<Mouse>/rightButton`, or `<Gamepad>/buttonSouth`.
- `Interactions` - additional trigger rules such as hold or tap.
- `Processors` - processors for the input value before it is passed into the action.
- `Groups` - the device group this binding belongs to.

If an action has an empty `Name`, no `Binding` block, or no `Binding.Path`, that action is simply not added to the game.

### How to Fill in inputs.json

Usually, this order is enough:

1. Add a new action with a clear and unique `Name` to `Actions`.
2. Choose the `Type` that matches your use case.
3. Set the default binding in `Binding.Path`.
4. In Lua code, get that action by the same name through [`InputActions:FindAction`](../../api/InputAction.md#findaction).

Practical example for a toggle:

```json
{
  "Actions": [
    {
      "Name": "ToggleSniperMode",
      "Type": "Button",
      "Binding": {
        "Path": "<Keyboard>/v"
      }
    }
  ]
}
```

Example for an axis or continuous value:

```json
{
  "Actions": [
    {
      "Name": "ZoomAmount",
      "Type": "Value",
      "Binding": {
        "Path": "<Mouse>/scroll/y"
      }
    }
  ]
}
```

In practice, the types are used like this:

- `Button` - regular presses, toggles, and hotkeys
- `Value` - actions that read a value: an axis, the mouse wheel, or an analog stick
- `PassThrough` - direct raw value forwarding without typical button behavior; useful for special cases where the module needs the unfiltered input stream
