<a id="module-folder-structure"></a>
### Структура папки модуля

В корневой директории модуля могут находиться следующие файлы:

- `module.json` - основной файл с информацией о модуле (обязательный)
- `scripts/main.lua` - код, выполняющийся на стороне клиента (обязательный)
- `scripts/server.lua` - код, выполняющийся на сервере
- `config.json` - пользовательские настройки модуля
- [`inputs.json`](#module-inputs-json) - пользовательские клавиши модуля
- `localization.csv` - таблица с переводами на разные языки

Также в директории модуля могут находиться необязательные папки с ресурсами:

- `sounds/` - папка для звуковых файлов, поддерживаемый формат: `wav`
- `images/` - папка для файлов изображений, поддерживаемый формат: `png`
- `scripts/` - папка для файлов скриптов, поддерживаемый формат: `lua`
- `ui/` - папка для файлов UI, поддерживаемые форматы: `uxml`, `uss`

<a id="module-tags"></a>
### Теги модуля

В `module.json` у модуля есть поле `Tags`. Это массив тегов, который используется для группировки модулей по назначению и для предупреждений о пересечении функций.

Пример:

```json
{
  "Tags": ["Crosshair", "Notifications"]
}
```

У модуля может:

- не быть тегов
- быть один тег
- быть несколько тегов

Если тегов нет, модуль просто попадает в группу без тегов. Если тегов несколько, игра считает, что модуль относится сразу к нескольким категориям.

Доступные теги:

- `Minimap` - модули миникарты
- `PingMarks` - модули меток и пингов
- `OverheadLabels` - подписи и элементы над объектами
- `Crosshair` - прицелы и связанные с ними HUD-элементы
- `Health` - отображение здоровья
- `Notifications` - отображение уведомлений на экране
- `MatchStatus` - статус матча, раунда и игровой фазы
- `CombatReport` - боевой отчет
- `Scoreboard` - таблица счета
- `Loadout` - экипировка и информация о снаряжении
- `BuyMenu` - меню покупки
- `GrenadePreview` - предпросмотр гранат и траекторий
- `Chat` - чат
- `ThreatIndicator` - индикаторы гранат и направления опасности
- `KillFeed` - лента убийств
- `Spectator` - интерфейс наблюдателя
- `DebugInfo` - отладочная информация

### Конфликты тегов

Если одновременно активны два или более модуля с одним и тем же тегом, игра помечает их как конфликтующие. Это не блокировка: такие модули могут быть запущены одновременно.

Важно понимать, что конфликт тегов означает наложение функциональности. Например, два модуля с тегом `Crosshair` могут одновременно рисовать свой прицел, а два модуля с тегом `Notifications` - одновременно выводить похожие уведомления.

То есть конфликты тегов влияют в первую очередь на интерфейс и поведение модулей: предупреждают, что несколько модулей пытаются делать одну и ту же задачу. Обычные теги не ограничивают запуск модуля автоматически.

<a id="reflex-flag"></a>
### Флаг Reflex

`Reflex` - отдельный флаг `IsReflex` в `module.json`.

Пример:

```json
{
  "IsReflex": true,
  "Tags": []
}
```

Модуль с таким флагом отличается от обычного тем, что у него есть серверная часть в файле `scripts/server.lua`. Когда игрок заходит на сервер, игра берет код из этого файла на клиенте и отправляет его на сервер для выполнения.

Для Reflex-модулей действует отдельное ограничение: одновременно может быть запущен только один такой модуль. Это поведение не связано с тегами и работает отдельно от системы конфликтов тегов.

<a id="client-module-execution"></a>
### Выполнение клиентских модулей

Клиентские модули выполняются параллельно с игрой. Несколько модулей также могут выполняться параллельно друг с другом.

Большинство результатов работы модулей применяется в начале следующего кадра. Например, движение камеры или изменение UI будет применено с задержкой в один кадр. При этом перед отрисовкой главный поток всё ещё дожидается завершения работы модулей за текущий кадр. Параллельное выполнение не устраняет это ожидание: если задать большие лимиты времени и модули будут их расходовать, игра будет тормозить.

Единственное исключение - [ImGui](../../api/ImGui.md). Нарисованный через него интерфейс отображается в том же кадре. Поэтому для всех элементов, которые должны позиционироваться относительно объектов в 3D-мире, настоятельно рекомендуется использовать ImGui.

Для часто обновляемых элементов и всего игрового HUD также настоятельно рекомендуется ImGui. Частые изменения UI приводят к повторным расчётам расположения и размеров элементов (layout), которые занимают существенное время главного потока. В идеале UI следует использовать только для окон, обычно скрытых во время игрового процесса. Подробнее о выборе API - в [гайде по интерфейсам](./3.UI.md#ui-or-imgui).

### Лимиты времени выполнения

Во время первичной инициализации файла `main.lua` модулю отводится 5 секунд. Если этот лимит будет превышен, модуль отключится до следующего перезапуска.

Также действуют лимиты времени выполнения за один кадр клиента и за один тик сервера:

| Параметр | Значение по умолчанию | Допустимый диапазон |
|---|---|---|
| Лимит отдельного клиентского модуля (`TimeLimitMs` в `module.json`) | `5 ms` | `0.1–100 ms` |
| Общий клиентский предел времени выполнения модуля | `10 ms` | `0.1–100 ms` |
| Лимит серверного модуля за один тик | `1 ms` | Фиксированное значение |

Для каждого клиентского модуля применяется меньшее из его собственного лимита и общего клиентского предела. Например, при собственном лимите `20 ms` и общем пределе `10 ms` модуль получит `10 ms` на кадр. Общий предел ограничивает каждый модуль, а не сумму времени всех модулей. Значения по умолчанию и диапазоны заданы в `Assets/Scripts/Modding/Config/ModulesConstants.cs`.

Увеличение лимита позволяет модулю выполнять больше работы за кадр, но может увеличить ожидание главного потока перед отрисовкой и снизить FPS.

При достижении лимита модуль приостанавливает выполнение и продолжает его с того же места на следующем кадре или тике.

<a id="module-inputs-json"></a>
### Файл inputs.json

`inputs.json` лежит в корне модуля и описывает собственные действия ввода, которые модуль добавляет в систему управления игры.

Минимальный пример:

```json
{
  "Actions": [
    {
      "Name": "ToggleSniperMode",
      "Type": "Button",
      "Binding": {
        "Path": "<Keyboard>/v"
      }
    }
  ]
}
```

Файл состоит из массива `Actions`. Каждый элемент массива описывает одно действие.

- `Name` - имя действия. По нему модуль потом ищет это действие через [`InputActions:FindAction`](../../api/InputAction.md#findaction).
- `Type` - тип действия. Поддерживаются `Button`, `Value` и `PassThrough`. Если поле не указано, игра использует `Button`.
- `Binding` - описание стартовой привязки клавиши или другого контрола.

Внутри `Binding` можно указать:

- `Path` - путь к контролу в формате Unity Input System. Это основное и обязательное поле, например `<Keyboard>/v`, `<Mouse>/rightButton`, `<Gamepad>/buttonSouth`.
- `Interactions` - дополнительные правила срабатывания, например удержание или тап.
- `Processors` - обработчики входного значения перед передачей в действие.
- `Groups` - группа устройств, к которой относится привязка.

Если у действия пустой `Name`, нет блока `Binding` или не указан `Binding.Path`, такое действие просто не будет добавлено в игру.

### Как заполнять inputs.json

Обычно достаточно такого порядка:

1. Добавьте в `Actions` новое действие с понятным и уникальным `Name`.
2. Выберите `Type` под вашу задачу.
3. Укажите стартовую привязку в `Binding.Path`.
4. В Lua-коде получите это действие по тому же имени через [`InputActions:FindAction`](../../api/InputAction.md#findaction).

Практический пример для переключателя:

```json
{
  "Actions": [
    {
      "Name": "ToggleSniperMode",
      "Type": "Button",
      "Binding": {
        "Path": "<Keyboard>/v"
      }
    }
  ]
}
```

Пример для оси или непрерывного значения:

```json
{
  "Actions": [
    {
      "Name": "ZoomAmount",
      "Type": "Value",
      "Binding": {
        "Path": "<Mouse>/scroll/y"
      }
    }
  ]
}
```

По смыслу типы используются так:

- `Button` - обычные нажатия, переключатели, горячие клавиши.
- `Value` - действия, которые читают значение: ось, колесо мыши, аналоговый стик.
- `PassThrough` - прямой пропуск значения без типичного поведения кнопки; нужен для особых сценариев, когда модулю важен "сырой" поток ввода.
